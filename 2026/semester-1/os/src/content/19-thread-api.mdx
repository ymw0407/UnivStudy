<Callout kind="summary" title="이 장의 목적">
앞 장에서 thread가 *왜 race condition을 만들고 왜 동기화가 필요한지* 를 봤다면, 이번 장은 **실제로 thread를 만들고 멈추고 동기화하는 API** 를 다룹니다. POSIX thread(`pthread`) 의 네 묶음 — <b>pthread_create / pthread_join / pthread_mutex_&#42; / pthread_cond_&#42;</b> — 를 시그니처 한 줄까지 뜯어봅니다.
</Callout>


## Thread Creation

```c
#include <pthread.h>

int pthread_create(
    pthread_t *thread, 
    // 생성된 스레드를 식별하기 위한 핸들이다. 나중에 이 스레드를 기다리거나 관리할 때 사용한다.
    const pthread_attr_t *attr,
    // `attr`은 스레드의 속성을 지정하는 인자다. 
    // 예를 들어 스택 크기나 스케줄링 관련 속성을 줄 수 있지만, 
    // 보통은 기본값을 쓰기 때문에 `NULL`을 넣는다.
    void *(*start_routine)(void*),
    // `start_routine`은 새 스레드가 실행할 함수다.
    // 쉽게 말하면 "스레드가 시작되면 어디부터 실행할 것인가?"를 알려주는 함수 포인터다.
    void *arg
    // `arg`는 그 함수에 넘겨줄 인자다.
    // 타입이 `void *`인 이유는 어떤 타입의 데이터든 포인터 형태로 넘길 수 있게 하기 위해서다.
);
```

세 번째 인자의 타입 `void *(*start_routine)(void*)` 은 처음 보면 별표·괄호가 너무 많아 헷갈리는데, **안에서 밖으로 한 겹씩** 벗기면 단순하다.

```c
void *(*start_routine)(void*)

start_routine 
// 타입이 정해지지 않은 포인터 하나를 인자로 받고, 
// 타입이 정해지지 않은 포인터 하나를 반환하는 함수
// `start_routine`은 어떤 함수를 가리키는 포인터이고,  

*start_routine
// `*start_routine`은 그 포인터가 가리키는 함수 자체

(*start_routine)(void *)
// `start_routine`이 가리키는 함수는 `void *` 하나를 인자로 받는다

void *(*start_routine)(void*)
// `start_routine`이 가리키는 함수는 `void *`를 반환한다
```

pthread는 `void *` 기반으로 인자와 반환값을 다룬다. 그래서 개발자가 직접 적절한 타입으로 캐스팅해야 한다.

<Callout kind="note" title="왜 `void *` 인가?">
C 에는 generic 이 없습니다. <code>void *</code> 는 <i>"어떤 타입이든 받을 수 있는 포인터"</i> 라는 약속이고, 대신 받는 쪽이 <b>본인이 알고 있는 타입으로 cast</b> 해야 의미가 살아납니다. pthread 가 <i>어떤</i> 함수든 받을 수 있게 만들기 위해 치른 trade-off 입니다.
</Callout>

```c
#include <pthread.h>

typedef struct __myarg_t {  
	int a;  
	int b;  
} myarg_t;

void *mythread(void *arg) {
    myarg_t *m = (myarg_t *) arg;
    // void *로 인자를 받았기 때문에 myarg_t 타입으로 casting
    printf("%d %d\n", m->a, m->b);
    // "10 20\n"
    return NULL;
    // 이 스레드 함수가 끝났고, 호출한 쪽에 돌려줄 결과 포인터는 없다 -> NULL
}

int main(int argc, char *argv[]) {
	pthread_t p;
	// p는 새로 만들어진 스레드의 ID를 저장할 변수  
	// pthread_t는 pthread 라이브러리가 스레드를 식별하기 위해 쓰는 전용 타입
	
	myarg_t args;
	args.a = 10;
	args.b = 20;
	
	int ret = pthread_create(&p, NULL, mythread, &args);
	// p에 새로 만들어진 thread의 tid를 넣음
	// NULL -> 옵션을 선택하지 않음 -> default
	// mythread라는 함수를 thread로 실행시킬 것임
	// args를 mythread 함수의 인자로 넘김
	// args 자체가 아니라 args의 주소(&args)를 mythread 함수의 인자로 넘김
	
	if (ret != 0) {  
		// 스레드 생성 실패  
	}
}
```

`pthread_create` 가 리턴된 그 순간부터 **main 과 child 두 thread 가 동시에** 진행한다. 그 흐름을 한 장으로 보면 이렇다.

<PthreadJoinTimeline caption="pthread_create 가 child 를 띄우는 순간 두 thread 가 동시에 진행한다. main 이 pthread_join 에 도달하면 child 가 return 할 때까지 잠들어 있다가, child 의 반환 포인터를 받아 깨어난다." />


## pthread_join

```c
int pthread_join(pthread_t thread, void **value_ptr);
// 특정 스레드가 끝날 때까지 기다리고, 그 스레드 함수의 반환값을 받아오는 함수
// `thread`는 기다릴 대상 스레드다.

// `value_ptr`은 스레드 함수가 반환한 값을 받아오기 위한 인자다. 
// 타입이 `void **`인 이유는, 스레드가 반환하는 값 자체가 `void *`이기 때문이다. 
// 그 `void *` 값을 함수 바깥에서 받아와야 하므로 포인터의 포인터 형태가 된다.

// `void **`는 "`void *` 값을 바꾸기 위한 포인터"
```

```c
pthread_join(p, NULL);
// `p`라는 ID를 가진 스레드가 끝날 때까지 main thread가 기다린다.
```

지정한 스레드가 끝날 때까지 기다린다. 스레드가 return한 값을 받아올 수도 있다.

```c
#include <stdio.h>
#include <pthread.h>
#include <assert.h>
#include <stdlib.h>

typedef struct __myarg_t {
	int a;
	int b;
} myarg_t;

typedef struct __myret_t {
	int x;
	int y;
} myret_t;

void *mythread(void *arg) {
	myarg_t *m = (myarg_t *) arg;
	printf("%d %d\n", m->a, m->b);
	myret_t *r = malloc(sizeof(myret_t));
	// stack이 아닌 heap에 넣음 -> 아래 내용 참고 stack에 넣어서 리턴하면 안됨
	r->x = 1;
	r->y = 2;
	return (void *) r;
}

int main(int argc, char *argv[]) {
	int rc;
	pthread_t p;
	myret_t *m;
	
	myarg_t args;
	args.a = 10;
	args.b = 20;
	pthread_create(&p, NULL, mythread, &args);
	pthread_join(p, (void **) &m);
	printf("returned %d %d", m->x, m->y);
	return 0;
}
```

지역변수의 lifetime이 끝난다 → stack frame이 사라진다 → 그 주소를 계속 쓰면 dangling pointer가 된다.

```c
int *foo() {
    int x = 10;
	return &x;   // 위험
}
```

<StackReturnDanger caption="foo() 실행 중에는 frame 안에 x=10 이 살아 있어 &x 가 유효하지만, 반환 직후 frame 이 사라지면(또는 다음 호출이 그 자리를 덮어쓰면) &x 는 dangling pointer 가 되어 역참조하는 순간 UB. thread 함수가 결과를 돌려주고 싶다면 반드시 malloc 으로 heap 에 잡아 그 포인터를 반환해야 한다." />

<Callout kind="warning" title="왜 stack 반환이 위험한가">
함수가 끝나면 그 함수의 stack frame 은 사라집니다. 주소 자체는 메모리 어딘가에 있지만, 그 자리는 곧 <b>다음 함수 호출</b> 이나 <b>다른 스레드의 stack</b> 이 덮어씁니다. 그 주소를 계속 들고 있는 포인터를 <b>dangling pointer</b> 라고 하고, 역참조하는 순간 운이 좋으면 쓰레기 값, 나쁘면 crash. 그래서 thread 함수가 결과 구조체를 돌려주고 싶다면 위 예제처럼 <code>malloc</code> 으로 <b>heap</b> 에 잡아 그 포인터를 반환해야 합니다.
</Callout>


## Locks

### Mutual Exclusion(상호 배제)

여러 스레드가 동시에 들어오면 안 되는 구역에, 한 번에 하나의 스레드만 들어가게 하는 것

### Mutex(mutual exclusion lock)

공유 자원에 동시에 접근하지 못하게 막는 자물쇠

### Atomic(원자적)

중간에 끼어들 수 없는 하나의 동작처럼 실행되는 것

### Mutex vs Atomic

```c
pthread_mutex_lock(&lock);
counter++;
other_value += counter;
printf("%d\n", counter);
pthread_mutex_unlock(&lock);
```

"이 구역 전체에 나 혼자 들어갈래" - mutex

```c
atomic_fetch_add(&counter, 1);
```

"이 연산 하나는 절대 중간에 끊기지 않게 해줘"

### Mutex vs Semaphore

Mutex는 보통:

```
한 번에 1명만 들어감
```

Semaphore는:

```
정해진 개수만큼 들어갈 수 있음
```

<Callout kind="tip" title="셋의 보호 대상이 다르다">
• <b>Mutex</b> — 여러 줄로 된 critical section <b>구역 전체</b>를 묶어서 보호.<br/>
• <b>Atomic</b> — <code>counter++</code> 같은 <b>단일 연산</b>이 hot path 라 lock 의 오버헤드까지 줄이고 싶을 때.<br/>
• <b>Semaphore</b> — "동시 진입 인원수 <b>N</b>" 을 두고 싶을 때 (예: DB 커넥션 풀이 4 개면 동시에 4 명까지).<br/>
보호 대상의 모양이 다르면 도구도 달라집니다.
</Callout>


## pthread_mutex 사용법

```c
pthread_mutex_t lock; 
// opaque type(불투명 타입)
// lock의 상태, lock을 잡고 있는 thread ID 등이 포함

pthread_mutex_lock(&lock);
x = x + 1;   // critical section
pthread_mutex_unlock(&lock);
```

lock은 critical section에 대한 동시 접근을 막는다. 즉, 공유 데이터 수정 구간을 한 번에 한 스레드만 실행하게 만든다.

락은 다른 스레드가 같은 critical section에 동시에 들어오지 못하게 막는 것이지, 현재 락을 잡은 스레드가 CPU에서 쫓겨나지 않게 보장하는 것은 아니다.

<Callout kind="warning" title="lock 은 context switch 를 막지 않는다">
헷갈리기 쉬운 포인트라 한 번 더 강조합니다. lock 을 든 채로도 timer interrupt 가 와서 <b>context switch 가 일어날 수 있습니다</b>. 그래도 안전한 이유는 <b>다른 thread 가 그 critical section 에 들어가지 못하기 때문</b> 이지, "lock 을 든 thread 가 CPU 에서 안 쫓겨나서" 가 아닙니다.
</Callout>

```c
// 정적 초기화 방식
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

// 동적 초기화 방식
int rc = pthread_mutex_init(&lock, NULL);
assert(rc == 0); // 0이면 성공, 0이 아니면 에러 코드를 반환함 -> 0이여야지 통과
```

```c
int pthread_mutex_trylock(pthread_mutex_t *mutex);
// 지금 당장 lock을 얻을 수 있으면 얻고, 못 얻으면 기다리지 않고 바로 실패한다.
// "lock을 반드시 얻어야 하는 상황"보다는, 
// 얻을 수 있으면 하고, 아니면 다른 일을 하자 같은 상황에서 사용
int pthread_mutex_timedlock(
	pthread_mutex_t *mutex, struct timespec *abs_timeout
);
// lock을 얻을 때까지 기다리긴 하는데, 지정한 시간까지만 기다린다.  
// 그 시간 안에 lock을 얻으면 성공하고, 시간이 지나면 실패한다.
```

**lock**
문 열릴 때까지 계속 기다림

**trylock**
문 열려 있으면 들어가고, 잠겨 있으면 바로 포기

**timedlock**
문 열릴 때까지 기다리되, 정해진 시간까지만 기다림

<LockVariantsComparison caption="lock 은 무한정 기다리고, trylock 은 즉시 포기, timedlock 은 지정 시간까지만 대기한 뒤 실패. 어떤 정책을 쓸지는 '응답성을 보장해야 하나' · '다른 일거리가 있나' 같은 요구사항에 따라 결정한다." />


## Condition Variable

```c
int pthread_cond_wait(pthread_cond_t *cond, pthread_mutex_t *mutex);  
// `pthread_cond_wait()`는 현재 스레드를 잠들게 한다.  
// 즉, 어떤 조건이 만족될 때까지 CPU를 낭비하면서 계속 확인하는 것이 아니라, 
// 잠들어 있다가 신호(signal)를 받으면 다시 깨어난다.
  
int pthread_cond_signal(pthread_cond_t *cond);
// 기다리고 있는 스레드 중 적어도 하나를 깨운다
```

```c
pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t init = PTHREAD_COND_INITIALIZER;

pthread_mutex_lock(&lock);

while (initialized == 0)
    pthread_cond_wait(&init, &lock);
// 왜 if가 아니라 while?
// `pthread_cond_wait()`에서 깨어났다고 해서 조건이 반드시 만족된 상태라는 보장이 없다.
// 
// `initialized`가 아직 0이면 기다린다.  
// 깨어난 뒤에도 다시 확인한다.  
// 진짜 `initialized != 0`이 되었을 때만 빠져나간다.

pthread_mutex_unlock(&lock);

--------------------------------------

pthread_mutex_lock(&lock);  
  
initialized = 1;
// 왜 필요하지?
// condition variable이다. 상태를 확인할 수 있는 상태 변수
pthread_cond_signal(&init);  
// signal이 없어도 되는거 아닌가?
// pthread_cond_wait을 하고 있는 쓰레드를 계속 while문으로 돌리면 낭비 -> spin lock
// 그렇기 때문에 이때 blocked state로 sleep을 시키는데, 이때 깨우려면 시그널을 보내야함
// wait에 들어간 init과 signal의 init이 같아야함.

pthread_mutex_unlock(&lock);
```

`init`이 condition variable이고, `initialized`는 실제 상태를 저장하는 일반 변수.

이 짧은 코드 안에서 두 thread 가 정확히 어떤 순서로 손을 주고받는지 한 장으로 보면 이렇다.

<CondVarProtocol caption="Thread A 는 lock 후 조건을 확인하고, 거짓이면 cond_wait — 이 함수는 'mutex 풀기 + 잠들기' 를 atomic 하게 수행한다. Thread B 가 lock 을 잡고 상태를 바꾼 뒤 signal 을 쏘면 A 가 깨어나는데, 이때 cond_wait 안에서 mutex 를 다시 잡아 주고 나서야 반환한다. 깨어난 A 는 while 로 한 번 더 검사한 뒤 빠져나간다." />

<Callout kind="note" title="cond_wait 이 mutex 를 인자로 받는 이유">
<code>pthread_cond_wait</code> 는 <b>"mutex 풀기 + 잠들기"</b> 두 동작을 <b>atomic</b> 하게 합칩니다. 따로 했다간 <i>"풀고 → 자기 직전에 다른 thread 가 signal → 그 신호를 놓치고 영원히 못 깨어남"</i> 이라는 <b>lost wakeup</b> 이 생기기 때문이죠. 그리고 깨어날 때도 <b>자동으로 mutex 를 다시 잡고</b> 반환합니다 — 그래서 wait 전후의 코드를 마치 풀린 적 없는 것처럼 짤 수 있습니다.
</Callout>

<Callout kind="tip" title="condition variable 과 state variable 의 역할 분리">
정리하면:<br/>
• <b>condition variable (<code>init</code>)</b> — 잠/깨우기의 동기화 채널. 값을 비교하거나 읽지 않습니다.<br/>
• <b>state variable (<code>initialized</code>)</b> — 실제 상태를 담는 보통 변수. <code>while</code> 의 조건 검사는 <b>이쪽</b>으로 합니다.<br/>
두 변수는 <b>반드시 같은 mutex 로 보호</b> 되어야 합니다. 그래야 "상태 변경 → signal" 이 한 덩어리로 보이고, missed wakeup 이 사라집니다.
</Callout>


## 컴파일

```bash
gcc -o main main.c -Wall -pthread
```

- `-Wall` — 가능한 경고는 다 켜기.
- `-pthread` — 컴파일·링크 모두에 pthread 설정을 추가. 단순 `-lpthread` 보다 **이쪽이 권장** 된다(`_REENTRANT` 같은 매크로도 함께 정의해 주기 때문).


## 한 줄 요약

<Callout kind="summary" title="Thread API 4 종 한눈에">
• <b>pthread_create</b> — 새 thread 시작. 4 번째 인자(<code>void *</code>)로 데이터 전달.<br/>
• <b>pthread_join</b> — thread 종료 대기 + 반환값 수신. ⚠️ 반환은 반드시 <b>heap</b>으로(<code>&local</code> 금지).<br/>
• <b>pthread_mutex_&#42;</b> — critical section 의 상호 배제. <code>lock</code> / <code>trylock</code> / <code>timedlock</code> 으로 대기 정책 선택.<br/>
• <b>pthread_cond_&#42;</b> — 조건이 만족될 때까지 잠들었다 깨기. 반드시 <code>while</code> 로 재검사, 항상 mutex 안에서.
</Callout>
